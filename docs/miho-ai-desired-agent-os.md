# 미호 AI 목표 시스템 정의

작성일: 2026-06-26
목적: 맥스가 원하는 미호 AI의 최종 지향점을 구현 기준으로 고정한다.

100점 스코어카드: `docs/miho-ai-100-point-scorecard.md`

## 한 줄 정의

미호 AI는 사용자의 요청을 이해하고, 필요한 도구와 에이전트를 스스로 편성하고, 산출물을 만들고, 검증 실패를 사용자에게 노출하지 않은 채 내부에서 다시 고쳐, 최종적으로 사용자에게 바로 쓸 수 있는 결과만 전달하는 자가개선 Agent OS다.

## 핵심 철학

미호는 챗봇이 아니다.

미호는 다음 네 가지를 모두 갖춘 운영체제여야 한다.

- 요청을 이해하는 라우팅 지능
- 일을 끝까지 수행하는 실행 루프
- 결과를 검수하고 다시 고치는 리뷰어 루프
- 실패를 기록하고 스스로 개선하는 Self-Harness

사용자가 보는 것은 중간 실패가 아니라 최종 결과여야 한다.

## 범용 OS 구성

미호 AI의 범용 구조는 학원 도구 자체와 분리해서 봐야 한다.

학원 도구는 각 도메인의 전용 엔진이다.

- 수시 추천 도구는 요청 범위의 가능한 학교를 누락하지 않아야 한다.
- 학종 리포트 도구는 생기부와 학교/학과 맥락을 정확히 반영해야 한다.
- PDF 도구는 텍스트, 줄맞춤, 여백, footer, 메타데이터, 첨부 가능성을 검증해야 한다.
- 스레드/학원 운영 도구는 현재 대화, thread memory, DB, 저장 파일 중 실제 근거를 찾아야 한다.

미호 AI의 범용 OS는 이 도구들을 감싸는 세 층이다.

- Hermes: 사용자 맥락을 읽고 도구 맵을 보고 실행 경로를 고르는 LLM 라우터
- Governance: 결과가 사용자 의도, 도메인 계약, 산출물 품질을 만족하는지 보는 LLM reviewer/QA 체계
- Self-Harness: 실패 포인트를 기록하고, 개선 후보를 만들고, 테스트/리뷰/rollback으로 스스로 강화하는 루프

이 세 층은 서로 대체하면 안 된다.

Hermes가 도구 품질을 대신하면 안 된다.
Governance가 도구 실행 없이 말로만 통과시키면 안 된다.
Self-Harness가 실시간 결과 전달을 대신하면 안 된다.

## 하드코딩 금지의 정확한 경계

맥스가 싫어하는 것은 Python 자체가 아니다.

문제는 Python 코드가 의미 판단을 하드코딩 문자열로 대신하는 것이다.

영구 원칙:

- 모든 에이전트 라우팅, 검증, reviewer 판정, Final QA, Self-Harness weakness mining/proposal은 LLM 기반이어야 한다.
- Python 코드는 실행, 측정, schema/path/security, 산식 일치, rollback 같은 물리 계약만 검증한다.
- Python 코드가 문자열/키워드/정규식으로 사용자 의도, 도메인 의미, 최종 답변 적합성을 막거나 통과시키면 실패다.
- deterministic check 결과는 LLM agent에게 넘기는 evidence여야 하며, agentic 판단 자체를 대체하면 안 된다.

금지되는 방식:

```text
답변에 "학종"이 들어 있음
-> 무조건 불합격
```

```text
답변에 "검증"이 들어 있음
-> 무조건 차단
```

```text
질문에 "PDF"가 들어 있음
-> 고정 템플릿 하나로 무조건 생성
```

맞는 방식:

```text
LLM router가 전체 대화, 사용자 의도, 도구 맵, 현재 산출물을 함께 본다
-> 이 요청은 학종 산출물인지, 학종이라는 단어가 포함된 거버넌스 리뷰인지 구분한다
-> 필요한 도구와 reviewer를 고른다
```

Python이 해도 되는 것:

- 파일이 존재하는지
- PDF footer 좌표가 페이지 밖으로 밀렸는지
- 첨부 경로가 Discord에서 보낼 수 있는지
- 산식 계산 결과가 일치하는지
- JSON schema가 맞는지
- secret/path가 노출됐는지
- rollback snapshot이 존재하는지

Python이 하면 안 되는 것:

- 사용자의 진짜 의도 판정
- 답변이 질문에 맞는지 최종 의미 판정
- 도메인 산출물이 충분한지 정성 판정
- PDF 디자인이 상담 자료로 보기 좋은지 최종 미감 판정
- 특정 단어 포함 여부만으로 통과/불합격 결정

정리하면 하드코딩 guard는 안전벨트일 뿐이다. 운전자는 LLM agent여야 한다.

## Agentic 품질 루프

미호의 정상 실행은 단방향 파이프라인이 아니다.

정상 구조:

```text
사용자 요청
-> Hermes LLM Router가 맥락 파악
-> 도구 맵 기반으로 domain agent/tool 선택
-> domain agent가 결과 생성
-> deterministic checks가 물리 계약 측정
-> LLM reviewer가 사용자 의도와 도메인 의미 검수
-> 실패하면 builder agent에게 재작업 지시
-> 다시 reviewer 검수
-> 통과하면 Final QA/Delivery Agent가 최종 정리
-> 사용자에게 결과 전달
-> outcome ledger 기록
```

리뷰어가 실패를 발견했을 때 사용자에게 실패 설명을 보내면 안 된다.

리뷰어는 다음 중 하나를 해야 한다.

- 같은 도구에 더 정확한 인자를 주고 다시 실행시킨다.
- PDF라면 템플릿, 여백, 줄바꿈, 페이지 분리 조건을 바꿔 다시 생성시킨다.
- 추천 결과라면 누락 지역, 제외 기준, 만점 가능성, 후보 범위를 다시 계산시킨다.
- 스레드 맥락 문제라면 DB보다 먼저 대화/저장 파일 근거를 확인하게 한다.
- 답변 형식이 틀렸다면 Final QA Agent가 사용자 요청 형식에 맞춰 다시 쓰게 한다.

사용자에게 전달되는 것은 이 루프가 통과한 결과여야 한다.

## 절대 원칙

### 1. 사용자는 내부 실패를 보지 않는다

사용자에게 아래 문구가 최종 답변으로 보이면 실패다.

- 확인 근거가 부족해 전달하지 않겠습니다.
- 검증 전이라 완료라고 말할 수 없습니다.
- 전용 도구/후검증 기록이 없어 전달할 수 없습니다.
- 같은 요청을 다시 보내주세요.
- 도구를 다시 실행해야 합니다.
- fallback, retry, recovery, guard, hook 같은 내부 용어

검증이 필요하면 미호 내부에서 검증한다.

PDF가 깨졌으면 다시 생성한다.
첨부 경로가 틀렸으면 안전한 경로로 옮겨 다시 첨부한다.
산식이 불확실하면 전용 계산 도구를 다시 호출한다.
답변이 질문과 안 맞으면 Final QA Agent가 다시 쓰게 한다.

사용자에게는 항상 현재 턴에서 가능한 최종 결과가 나와야 한다.

### 2. Final Delivery는 문지기가 아니라 완성 담당자다

Final Delivery의 역할은 차단 문구를 만드는 것이 아니다.

Final Delivery는 다음을 수행해야 한다.

- 최종 답변이 사용자 질문에 맞는지 확인
- 내부 검증 문구, stack trace, provider 오류, 코드 용어 노출 제거
- 파일 첨부 경로가 Discord에서 전송 가능한 위치인지 확인
- `MEDIA:` 태그가 실제 파일을 가리키는지 확인
- 허용되지 않은 경로면 안전한 staging 경로로 복사
- 첨부 누락이면 재첨부 가능한 형태로 복구
- 확정 산출이 불가능한 경우에도 대기 안내가 아니라 현재 정보 기준의 결론과 필요한 입력을 결과로 답변

이름은 Gate보다 Orchestrator에 가깝다.

### 3. 실패는 메시지가 아니라 실행으로 흡수한다

나쁜 설계:

```text
검증이 필요해서 지금은 답하지 않겠습니다.
```

맞는 설계:

```text
검증 실패
-> 필요한 도구 재실행
-> 결과 재생성
-> reviewer 재검수
-> Final QA 재검수
-> 정상 결과 전달
```

미호는 실패를 설명하는 봇이 아니라 실패를 흡수하는 OS여야 한다.

## 라우팅 원칙

미호는 사용자의 말 자체를 이해해야 한다.

사용자가 “pdf로 줘”라고 하면:

- PDF 생성 도구를 선택해야 한다.
- 기존 텍스트 답변을 다시 설명하면 안 된다.
- 수동 HTML/PDF 손제작으로 우회하면 안 된다.
- 정식 템플릿/품질 검증/첨부 계약을 통과한 파일만 줘야 한다.

사용자가 “국민대반 명단 줘봐”라고 하면:

- 먼저 현재 스레드 맥락을 봐야 한다.
- 스레드에 추가한 명단이 있으면 DB만 보겠다고 하면 안 된다.
- DB, thread memory, 최근 대화, 저장 파일 중 권위 있는 근거를 찾아야 한다.

LLM Dispatcher는 도구 맵을 받아야 한다.

- 어떤 도구가 무엇을 하는지
- 어떤 도구가 PDF를 만드는지
- 어떤 도구가 첨부 경로를 보정하는지
- 어떤 도구가 수시 추천 전체 후보를 뽑는지
- 어떤 도구가 스레드 명단을 읽는지

라우팅은 키워드만으로 끝나면 안 된다. 키워드는 후보 신호이고, 최종 판단은 LLM dispatcher가 맥락과 도구 맵을 보고 해야 한다.

## Reviewer 구조

미호에는 reviewer가 여러 층으로 있어야 한다.

### Deterministic Reviewer

기계적으로 검증 가능한 것은 코드가 본다.

- PDF 파일 존재
- PDF 페이지 수
- PDF footer 하단 좌표
- 메타데이터 제거
- 한글 텍스트 추출 가능 여부
- 파일 크기
- manifest canonical 여부
- 첨부 가능 경로
- 산식 숫자 일치
- safe path 여부

### Domain LLM Reviewer

도메인 의미는 LLM reviewer가 본다.

- 학종 리포트가 학생 생기부와 학교 방향에 맞는가
- 수시 추천이 사용자의 요청 범위를 임의로 잘라내지 않았는가
- “전체 후보” 요청인데 상향이라는 이유로 누락하지 않았는가
- 운동 프로그램 PDF가 현장 코칭 자료처럼 자연스러운가
- 답변이 사용자가 실제로 물은 것에 답하고 있는가
- deterministic reviewer의 측정값을 근거로 삼되, 그 측정값이 의미판단을 대신하게 하지 않았는가

### Final QA Agent

최종 답변 직전의 마지막 LLM 검수다.

- 질문에 맞는가
- 내부 사고/검증 문구가 새지 않았는가
- 완료/첨부/계산 claim이 evidence와 맞는가
- 사용자가 원하는 형식으로 결과가 나왔는가

Final QA Agent는 “검수 실패”를 사용자에게 말하는 역할이 아니다. 실패하면 이전 단계로 돌려 다시 만들게 하는 역할이다.

## PDF/첨부 산출물 원칙

PDF는 단순 파일 생성이 아니다.

PDF 요청은 다음 계약을 통과해야 한다.

- HTML-first 또는 정식 템플릿 기반 생성
- 폰트/줄바꿈/여백/페이지 분리 검증
- footer/header 위치 검증
- 메타데이터 제거
- 한글 텍스트 추출 검증
- 파일 크기 검증
- contact sheet 또는 페이지 이미지 기반 시각 검수
- Discord 첨부 가능 경로 staging
- `MEDIA:` 태그 또는 플랫폼 첨부 계약 검증

PDF가 깨지면 사용자에게 깨진 PDF를 주면 안 된다.

```text
PDF 생성
-> 품질 검증 실패
-> 내용 압축 또는 템플릿 조정
-> PDF 재생성
-> 다시 검증
-> 통과본만 첨부
```

## Repair / Retry Executor

retry는 JSON 계약만 있으면 부족하다.

미호는 실제 executor가 있어야 한다.

```text
reviewer: retry_needed
-> retry_tools 확인
-> retry_args 확인
-> 도구 자동 재실행
-> 결과 재검수
-> 통과하면 최종 전달
-> 실패하면 repair 전략 변경 후 재시도
-> 정해진 한계까지 실패하면 대기 안내가 아니라 현재 정보 기준의 결론과 필요한 입력 제공
```

사용자에게 “다시 실행해야 합니다”라고 말하는 것은 실패다.

## Self-Harness 목표

Self-Harness는 후보 제안기가 아니라 실제 자동 개선 루프여야 한다.

목표 흐름:

```text
실패 발생
-> Outcome Ledger 기록
-> 반복 실패 mining
-> LLM weakness miner 분석
-> LLM proposer가 개선 후보 생성
-> shadow candidate 생성
-> held-in / held-out 테스트 생성
-> 테스트 실행
-> domain reviewer 검수
-> promotion judge 판정
-> active registry 반영
-> post-activation regression
-> 실패 시 자동 rollback
```

사용자 승인 없이도 개선될 수 있어야 한다.
다만 rollback과 regression 검증은 필수다.

자가개선은 무작정 코드 수정이 아니다.

- 실패를 증거로 모은다.
- 작은 후보로 만든다.
- 검증한다.
- 활성화한다.
- 나빠지면 되돌린다.

Self-Harness는 두 시간축을 가져야 한다.

### 실시간 개선 루프

사용자에게 보내기 전 실패가 발견되면 같은 턴 안에서 복구한다.

```text
Final QA/Reviewer 실패
-> 실패 이유를 ledger에 기록
-> 필요한 도구/agent 재실행
-> 결과 재생성
-> reviewer 재검수
-> 통과본 전달
```

이 루프는 “나중에 해줄게”를 없애기 위한 즉시 실행 루프다.

### 사후 개선 루프

이미 사용자에게 새어나간 실패나 반복되는 실패는 Self-Harness가 수집한다.

```text
사용자 불만 또는 실패 로그
-> failure event 생성
-> 반복 패턴 mining
-> LLM weakness miner 분석
-> LLM proposer 개선안 생성
-> 테스트/리뷰/rollback 계약 통과
-> 활성화
```

새벽 cron은 이 사후 개선 루프를 돌릴 수 있다.
하지만 새벽 루프만으로는 충분하지 않다.

사용자가 “별로다”, “틀렸다”, “PDF가 구리다”, “결과가 안 나왔다”라고 말하면 그것은 단순 대화가 아니라 즉시 처리해야 하는 quality failure다.

사용자 피드백 failure event에는 최소한 다음이 남아야 한다.

- 원래 사용자 요청
- 미호가 실제로 보낸 답변
- 사용자가 지적한 문제
- 사용한 도구와 산출물 경로
- reviewer가 놓친 검수 항목
- 다음 실행에서 고쳐야 할 도구/agent/playbook

이 기록은 다음 두 곳에 동시에 쓰인다.

- 같은 유형 요청의 실시간 재발 방지
- Self-Harness의 자동 개선 후보 생성

## 도구 맵과 라우터 계약

LLM router는 도구 이름만 보는 것이 아니라 도구 맵을 받아야 한다.

도구 맵에는 다음이 포함되어야 한다.

- 도구가 해결하는 사용자 작업
- 필수 입력과 선택 입력
- 산출물 타입
- PDF/첨부/계산/검색/스레드조회 같은 side effect
- 후속 reviewer
- 실패 시 재시도 전략
- 같은 작업을 처리하는 다른 후보 도구

예시:

```text
사용자: 정수 수시 실기전형으로 수도권, 강원, 충청권 전체 추천해서 PDF로 줘

Hermes 판단:
- 작업: 수시 실기전형 전체 후보 추천 + PDF 전달
- 도구: academy_practical_reco_all_candidates
- 옵션: 지역 = 수도권/강원/충청, 전체 후보 = true, 상향 임의 제외 금지
- 산출물 reviewer: 수시 추천 reviewer + PDF layout reviewer
- delivery: Discord attachment staging 필요
```

```text
사용자: 국민대반 숭실대반 명단 줘봐

Hermes 판단:
- 작업: 현재 스레드에서 누적된 반 편성 명단 조회
- 1차 근거: thread memory/recent messages
- 2차 근거: 저장 파일
- 3차 근거: 학원 DB
- 금지: DB 결과 없음만 보고 명단 확정 불가라고 답하기
```

이 계약이 있어야 “키워드 regex”가 아니라 “맥락 기반 도구 선택”이 된다.

## 사용자 경험 기준

미호의 최종 사용자 경험은 단순해야 한다.

예를 들어 사용자가 “동하 대전대 학종 리포트 pdf로 줘”라고 하면 내부에서는 다음이 돌아야 한다.

```text
학생 확인
생기부 조회
학교/학과 프로필 조회
리포트 content 생성
PDF 생성
레이아웃 검증
도메인 reviewer 검수
첨부 경로 보정
Final QA 검수
첨부 전달
ledger 기록
```

사용자에게 보이는 것은 “여기 있어.”와 첨부 파일뿐이어야 한다. 중간 실패, 검증 로그, retry 지시는 사용자에게 보이지 않는다.

## ET Dev OS와 미호 AI의 차이

ET Dev OS는 개발 작업자다.

- repo 읽기
- 코드 수정
- 테스트
- 배포
- 커밋/푸시 판단
- 개발 품질 루프

미호 AI는 설치형 운영 에이전트다.

- Discord/사용자 요청 처리
- 학원/입시/첨부/PDF/업무 도구 운영
- 도구 라우팅
- 산출물 전달
- self-harness 개선
- 사용자-facing 품질 보장

둘 다 자가개선 목표를 가지지만, 같은 방식으로 붙이면 안 된다.

ET Dev OS의 자가개선은 개발 workflow와 repo 품질을 개선한다.
미호 AI의 자가개선은 사용자 요청 처리, 도구 선택, 산출물 검증, 첨부 전달, 운영 규칙을 개선한다.

## 성공 판정

미호가 목표 상태에 가까워졌다고 말하려면 다음이 모두 되어야 한다.

- 사용자가 요청한 형식의 결과가 항상 나온다.
- 내부 실패 문구가 사용자에게 노출되지 않는다.
- 전용 도구가 필요한 작업은 자동으로 해당 도구를 탄다.
- PDF/첨부 산출물은 실제 열어보고 검증한 것만 전달된다.
- reviewer가 단순 존재가 아니라 실패 시 재생성 루프를 촉발한다.
- Final QA Agent가 질문 적합성을 LLM으로 검수한다.
- Self-Harness가 반복 실패를 자동 개선 후보로 만들고 검증 후 반영한다.
- regression 실패 시 자동 rollback한다.
- 하드코딩 guard는 실행/측정/보안 계약에만 쓰이고, 의미 판단은 LLM agent가 맡는다.

## 최종 문장

미호 AI의 목표는 “잘 답하는 봇”이 아니다.

미호 AI의 목표는 사용자가 원하는 결과를 끝까지 만들어내고, 실패를 내부에서 흡수하며, 반복 실패를 스스로 고쳐 점점 더 강해지는 자율 Agent OS다.
