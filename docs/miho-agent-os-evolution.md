# Miho AI 시스템 진화 정리: Prompt에서 Agent OS까지

## 한 줄 결론

미호의 현재 위치는 **Harness 중심의 에이전트**이고, 감시 에이전트와 후검증 구조가 붙으면서 **Loop 단계에 진입하는 중**이다.

다음 단계는 단순히 더 많은 서브에이전트를 붙이는 것이 아니라, 에이전트들이 어떤 권한과 규칙 아래 움직일지 정하는 **Governance Engineering**, 즉 **Agent OS화**다.

```text
Prompt
→ Context
→ Harness
→ Loop
→ Governance / Agent OS
→ Institution / Company-in-a-box
```


## 1. Prompt Engineering

초기 AI 활용의 중심은 프롬프트였다.

> “어떻게 말해야 AI가 잘 답하나?”

핵심 자산은 좋은 지시문이었다.

```text
좋은 프롬프트 = 좋은 답변
```

하지만 프롬프트 중심 구조는 한계가 있다.

- 매번 사용자가 잘 물어봐야 한다.
- 기억이 약하다.
- 업무가 이어지지 않는다.
- 실행과 검증이 약하다.
- 사용자의 실제 조직 맥락을 깊게 반영하기 어렵다.


## 2. Context Engineering

다음 단계는 컨텍스트였다.

> “AI가 무엇을 알고 있어야 일을 잘하나?”

여기서 RAG, 메모리, 프로젝트 파일, 대화 기록, 사용자 프로필, 도메인 문서가 중요해졌다.

```text
좋은 컨텍스트 = 좋은 판단
```

미호도 이 단계에서 단순 챗봇을 벗어났다.

미호는 다음과 같은 맥락을 가진다.

- 맥스체대입시 업무 맥락
- PACA / Peak / 정시엔진 / 수시엔진
- 학생 관리, 상담, 입시, 학원 운영 도메인
- Discord 워크스페이스
- 사용자 선호와 반복 교정 기록
- 프로젝트 파일과 코드베이스
- 스킬과 업무 규칙

컨텍스트가 붙으면서 AI는 단순 응답기가 아니라 **맥락을 가진 업무 파트너**가 된다.


## 3. Harness Engineering

그다음은 하네스다.

> “AI가 어떻게 보고, 손대고, 검증하고, 되돌릴 수 있나?”

하네스는 AI에게 실행 환경을 붙이는 단계다.

```text
좋은 하네스 = 좋은 실행력
```

하네스의 구성 요소는 다음과 같다.

- 파일 읽기와 수정
- 코드 변경
- 테스트 실행
- 브라우저 조작
- 컴퓨터 사용
- 도구 호출
- API 연동
- 스킬 로딩
- 승인 정책
- 샌드박스
- 체크포인트
- 로그와 검증

현재 미호의 본체는 강하게 **하네스형 에이전트**에 가깝다.

미호는 이미 다음을 수행한다.

- 도구를 사용한다.
- 파일과 코드를 다룬다.
- 테스트를 돌린다.
- Discord에서 업무를 처리한다.
- PACA/Peak/학원 도메인 도구를 호출한다.
- 산출물을 만들고 전달한다.
- 크론과 스케줄 작업을 처리한다.
- 스킬을 읽고 절차를 따른다.
- 산출물 전달 전 검증을 시작했다.

즉, 미호는 단순한 모델이 아니라 **작업장**을 가진 에이전트다.


## 4. Loop Engineering

하네스 다음은 루프다.

> “AI가 한 번 실행하고 끝나는 것이 아니라, 관찰하고, 검증하고, 실패를 학습하고, 다음 실행에 반영하나?”

진짜 루프는 단순 반복이 아니다.

```text
관찰
→ 판단
→ 실행
→ 검증
→ 실패 기록
→ 규칙/스킬/하네스 개선
→ 다음 실행에 반영
```

미호는 이미 루프의 초입에 들어왔다.

현재 미호에 붙기 시작한 루프 요소는 다음과 같다.

- `decision_twin`: 요청 의도와 도구 라우팅 점검
- `result_reviewer`: 산출물 전달 전 후검증
- `pre_tool_guard`: 위험한 우회 처리 차단
- `transform_tool_result`: 도구 결과를 전달 전 재검토
- `skill_curator`: 실패 패턴과 스킬 개선 후보 기록
- `Evolution OS`: 실패 패턴을 하네스 규칙으로 승격
- `cron/watchdog`: 반복 감시와 자동 실행
- `harness rules`: 반복 실패에서 나온 운영 규칙

따라서 현재 미호의 위치는 이렇게 볼 수 있다.

```text
Prompt: 통과
Context: 강함
Harness: 핵심 단계
Loop: 초기~중기 진입
Agent OS: 입구
Institution: 아직 아님
```

더 짧게 말하면:

```text
현재 미호 = 두뇌 + 작업장 + 일부 감시자
다음 미호 = 작업팀 + 감시자 + 판례집 + 운영규칙 + 자동개선 루프
```


## 5. 다음 단계: Governance Engineering

루프가 생기면 다음 질문은 바뀐다.

이전 질문은 이것이었다.

> “AI가 할 수 있나?”

다음 질문은 이것이다.

> “AI가 어디까지 자율적으로 움직여도 되는가?”

그리고 그 다음 질문은 이것이다.

> “AI 팀이 스스로 좋아지게 하려면 어떤 헌법이 필요한가?”

그래서 루프 다음 단계는 **Governance Engineering**이다.

Governance Engineering은 다음을 정한다.

- 어떤 에이전트가 어떤 권한을 가지는가?
- 어떤 작업은 자동 실행 가능한가?
- 어떤 작업은 사람 승인이 필요한가?
- 어떤 실패가 규칙으로 승격되는가?
- 어떤 스킬 변경은 롤백 가능해야 하는가?
- 어떤 산출물은 후검증 없이는 전달하면 안 되는가?
- 어떤 도구는 특정 업무에서 금지되는가?
- 성과와 실패를 어떻게 기록하고 측정하는가?

즉, 다음 진화는 단순히 “서브에이전트 추가”가 아니라 **에이전트 조직의 운영체제화**다.


## 6. Agent OS의 핵심 구성 요소

### 6.1 Router가 아니라 Dispatcher

현재의 라우터는 요청 의도를 분류한다.

```text
이건 학원 업무다.
이건 코딩 업무다.
이건 건강 로그다.
이건 운영 업무다.
```

하지만 다음 단계의 디스패처는 작업팀을 편성한다.

```text
이 업무는 어떤 에이전트 조합으로 처리할 것인가?
누가 조사하고, 누가 초안을 만들고, 누가 검수할 것인가?
몇 단계까지 자동으로 진행하고, 어디서 멈출 것인가?
```

이것이 단순 라우팅과 Agent OS의 차이다.


### 6.2 Memory가 아니라 Case Law

현재 메모리는 기억이다.

다음 단계에서는 기억이 **판례**처럼 작동해야 한다.

```text
예전에 비슷한 요청에서 어떤 실수를 했나?
그때 어떤 도구를 써야 했나?
사용자가 무엇을 교정했나?
최종적으로 통과한 산출물은 어떤 구조였나?
```

이렇게 되면 미호는 단순히 기억하는 것이 아니라 **맥스 조직의 업무법**을 갖게 된다.


### 6.3 Skill이 아니라 Playbook

스킬은 특정 도구나 절차를 설명한다.

```text
이 도구는 이렇게 써라.
```

플레이북은 업무 전체를 운영한다.

```text
이 업무 유형은 어떤 순서로 처리하고,
누가 검수하고,
무엇을 금지하고,
어떤 형식으로 전달하고,
무엇을 기억에 남길 것인가?
```

필요한 플레이북 예시는 다음과 같다.

- 입시 상담 자료 플레이북
- 학생카드 플레이북
- 건강 로그 플레이북
- 미호 코드 업데이트 플레이북
- Discord 워크스페이스 운영 플레이북
- 학원 운영 자동화 플레이북

각 플레이북은 다음 필드를 가져야 한다.

```text
trigger
required context
required tools
forbidden tools
review gates
retry policy
delivery format
memory policy
rollback policy
```


### 6.4 단일 루프가 아니라 Multi-loop

다음 단계의 미호는 하나의 루프만 도는 구조가 아니라 여러 루프가 병렬로 돌아야 한다.

```text
작업 루프: 지금 요청을 끝낸다.
품질 루프: 결과물 오류를 잡는다.
기억 루프: 배운 점을 저장한다.
하네스 루프: 시스템 규칙을 고친다.
운영 루프: 크론/감시/알림을 돈다.
제품 루프: 사용자 피드백을 기능으로 바꾼다.
```

이 구조가 만들어지면 미호는 단순 에이전트가 아니라 **작은 운영체제**가 된다.


## 7. 미호 다음 빌드 방향

### 7.1 Agent Council

역할별 판단기를 명시적으로 묶는다.

```text
decision_twin: 요청 의도 판단
tool_contract_guard: 도구 계약 위반 감시
result_reviewer: 결과물 검수
memory_judge: 기억 저장 여부 판단
evolution_judge: 실패 패턴 승격 여부 판단
risk_judge: 사람 승인 필요 여부 판단
```

현재 일부는 이미 존재한다.

다음 단계는 이것을 암묵적 훅 모음이 아니라 **명시적 council 구조**로 정리하는 것이다.


### 7.2 Playbook Registry

업무 유형별 실행 헌장을 만든다.

예시:

```text
admission_consulting
student_card
health_log
miho_code_update
discord_workspace_management
academy_operations
```

각 playbook은 다음을 정의한다.

```text
트리거
필수 컨텍스트
필수 도구
금지 도구
검증 게이트
재시도 정책
전달 형식
기억 저장 정책
```


### 7.3 Outcome Ledger

작업 결과를 단순 로그가 아니라 성과 장부로 저장한다.

```text
요청 유형
사용 도구
걸린 시간
실패 횟수
반려 사유
최종 산출물
사용자 피드백
다음 규칙 후보
```

이 장부가 있어야 미호가 “느낌상 좋아지는 것”이 아니라 **측정 가능하게 좋아지는 것**이 된다.


### 7.4 Promotion Pipeline

실패를 바로 시스템 규칙으로 바꾸면 위험하다.

따라서 다음과 같은 승격 파이프라인이 필요하다.

```text
실패 발생
→ 후보 기록
→ 반복성 확인
→ 안전성 검증
→ 스킬/하네스/플레이북 규칙으로 승격
→ 롤백 가능 상태 유지
```

현재 Evolution OS는 이 방향을 이미 잡고 있다.

다음은 승격 대상을 더 넓히는 것이다.

```text
skill update
harness rule update
tool contract update
playbook update
router rule update
reviewer policy update
```


### 7.5 Simulator / Drill

진짜 강한 에이전트는 실제 사용자 요청만 기다리지 않는다.

스스로 훈련 케이스를 돌려야 한다.

예시:

```text
가짜 상담 자료 요청 20개
가짜 추천 흐름 요청 20개
가짜 학생 자료 업로드 오류 20개
가짜 Discord 미디어 전달 실패 20개
가짜 코딩 수정/테스트 실패 20개
```

검증 항목:

```text
정확한 도구를 골랐는가?
금지 도구를 쓰지 않았는가?
검증 실패 후 재시도했는가?
민감정보를 노출하지 않았는가?
확정하면 안 되는 내용을 확정하지 않았는가?
산출물 형식이 맞는가?
```

이 단계가 들어가면 미호는 **실제 업무를 하며 배우는 에이전트**를 넘어 **훈련장까지 가진 에이전트**가 된다.


## 8. 전체 진화 지도

```text
Prompt Engineering
- 좋은 지시문을 찾는 단계

Context Engineering
- 좋은 판단을 위해 기억과 지식을 붙이는 단계

Harness Engineering
- 도구, 파일, 브라우저, 테스트, 승인, 샌드박스를 붙이는 단계

Loop Engineering
- 관찰, 실행, 검증, 실패 기록, 개선 반영이 도는 단계

Governance Engineering
- 에이전트의 권한, 규칙, 책임, 승격, 롤백을 설계하는 단계

Institution Engineering
- 조직의 업무법과 운영 습관을 내장한 전용 AI 조직으로 발전하는 단계
```


## 9. 미호의 포지션

현재 미호는 다음과 같이 정의할 수 있다.

```text
미호는 프롬프트 기반 챗봇이 아니다.
미호는 컨텍스트를 가진 하네스형 에이전트이며,
감시 에이전트와 Evolution OS를 통해 루프 단계로 진입 중인 전용 업무 운영체제다.
```

더 제품적으로 표현하면:

```text
범용 AI는 좋은 두뇌다.
미호는 두뇌에 작업장, 기억, 도구, 감시자, 업무 규칙을 붙인 전용 작전실이다.
```

그리고 다음 미호는 이렇게 가야 한다.

```text
작업을 수행하는 에이전트
→ 작업을 검증하는 에이전트
→ 실패를 기록하는 에이전트
→ 규칙을 승격하는 에이전트
→ 업무법을 운영하는 Agent OS
```


## 10. 최종 정리

맥스가 말한 흐름은 맞다.

```text
프롬프트
→ 컨텍스트
→ 하네스
→ 루프
```

그리고 그 다음은 다음이다.

```text
거버넌스
→ Agent OS
→ 조직화된 AI 운영체제
```

핵심은 이것이다.

> 모델 경쟁은 계속 평준화된다.
> 하지만 특정 조직의 업무법, 판례, 플레이북, 검증 루프를 가진 Agent OS는 쉽게 복제되지 않는다.

미호가 가야 할 방향은 단순히 더 똑똑한 AI가 아니라, **맥스체대입시와 Layer8 업무를 계속 학습하고 운영하는 전용 Agent OS**다.
